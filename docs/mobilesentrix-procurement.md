# MobileSentrix Procurement

Admin-only workflow for buying, from MobileSentrix, the MobileSentrix items that Eclise customers have **already paid for**.

```
Customer payment confirmed (PaymentFinalizer)
        ↓
mobilesentrix_buffer            status = Pending
        ↓  admin selects quantities
MobileSentrixProcurementService
        ├── mobilesentrix_orders
        └── mobilesentrix_order_items
        ↓
buffer processed_quantity updated → Pending / Processed
        ↓
(future) MobileSentrixOrderGateway → MobileSentrix API
```

Automatic API ordering is **not** implemented. An administrator places the order with MobileSentrix manually and records the supplier reference afterwards.

## Trigger

Requirements are queued only from `PaymentFinalizer::markPaid` — the application's single authoritative paid transition, which for Stripe runs from the signed webhook. Adding to cart, starting checkout, issuing an invoice, returning from a gateway redirect, or accepting a repair proposal all queue nothing.

Queueing runs **inside** the finalization transaction so a paid MobileSentrix item can never exist without its procurement requirement. It is a pure insert from data already loaded in that transaction — no catalogue lookup and no network call — so it cannot realistically fail and strand a customer payment. Prices are resolved later, when the admin creates the procurement order.

## What qualifies

| Origin | Qualifies | Excluded |
| --- | --- | --- |
| Shop order line | `order_items.source = 'Mobilesentrix'` (a MobileSentrix device) | Eclise-owned products (`source = 'Eclise'`) |
| Repair | The **selected** option of an active part group, when it is a real catalogue part backed by the MobileSentrix API | "I Have the Parts", unselected alternatives, deactivated options, locally sourced parts |

Classification uses authoritative source metadata only — never product names or SKU prefixes.

## Idempotency

Each requirement is keyed on **the purchased line that caused it**, not on the payment event:

| `source_reference_type` | `source_reference_id` |
| --- | --- |
| `order_item` | `order_items.id` |
| `repair_part_selection` | `repair_part_selections.id` |

A unique index on `(source_reference_type, source_reference_id)` enforces it. A Stripe webhook replayed three times produces one row, while the same SKU bought again in a different order is a different line and is queued correctly.

These two columns are additions beyond the preliminary schema. Without them, no combination of the listed fields distinguishes "duplicate webhook" from "legitimate repeat purchase".

## Partial quantities

`processed_quantity` (Option A) tracks how much of a requirement has been ordered.

```
remaining = quantity - processed_quantity
status    = Processed when processed_quantity >= quantity, otherwise Pending
```

Ordering 3 of 5 leaves 2 available and the row Pending. Buffer rows are never deleted or split — processed rows are procurement history.

## Pricing

Procurement lines store what Eclise pays MobileSentrix, never what the customer paid.

The cost is read from `MarkupPriceResult::base_price` — the value Eclise markup is applied *to* — via the existing `MobileSentrixMarkupService`:

- Parts: `api_price` (falling back through the service's own chain)
- Devices: `price`

It is never derived by reversing markup from a selling price. `mobilesentrix_order_items.mobilesentrix_price` snapshots the cost at order time, so historical orders stay accurate when the catalogue changes.

`mobilesentrix_tax` defaults to `0.00`; there is no authoritative supplier tax rule, so the admin enters the real figure after placing the order rather than the system fabricating one.

## Order numbering

`MS-ORD-{year}-{0000001}`, generated by `MobileSentrixOrderNumberGenerator`, which mirrors `OrderNumberGenerator` (row-locked sequence table). It uses its own `mobilesentrix_order_number_sequences` table because `order_number_sequences` is keyed on year alone and cannot host a second series.

Two distinct numbers exist and must not be conflated:

| Column | Meaning |
| --- | --- |
| `mobilesentrix_buffer.order_number` | The **Eclise customer** shop order that caused the requirement |
| `mobilesentrix_order_items.order_number` | Same — preserved for traceability |
| `mobilesentrix_orders.order_number` | The **internal Eclise procurement** order number |
| `mobilesentrix_orders.supplier_order_number` | The reference MobileSentrix returns, entered manually |

`supplier_order_number` is an addition, so the internal identifier is never overwritten.

## Concurrency

`createProcurementOrder` runs in one transaction, takes `lockForUpdate()` on every selected buffer row **before** validating, and revalidates remaining quantity against the locked rows. Two admins cannot both pass validation against the same remaining quantity. Any invalid line rolls back the whole order — no partially created procurement order survives.

## Totals

All arithmetic runs in integer minor units via `App\Support\Money`, matching the payment module.

```
subtotal = Σ (quantity × mobilesentrix_price) + mobilesentrix_tax
total    = subtotal + tax + shipping_cost - shipping_discount_amount
```

## Traceability

Customer requirements are never merged in the database. `mobilesentrix_order_items` keeps `customer_id`, `order_number`, `repair_number` and `mobilesentrix_buffer_id`, so every supplier line traces back to the customer transaction that caused it. The cart screen shows aggregate demand per SKU as buying guidance only.

## Statuses

- Buffer: `Pending` → `Processed`
- Order: `Ordered` → `Received` or `Returned`; `Received` → `Returned`. `Returned` is terminal.

Marking an order Received deliberately does **not** touch Shop or Repair inventory. No inventory receiving subsystem is invented here.

## Permissions

Seeded into the existing `permissions` catalogue, following the Stage 2 payment convention:

`mobilesentrix.buffer.view`, `mobilesentrix.orders.view`, `mobilesentrix.orders.create`, `mobilesentrix.orders.update`, `mobilesentrix.orders.receive`, `mobilesentrix.orders.return`

Enforcement is the existing `admin` middleware on every route, which is what actually protects the admin area today — a user carries a single `permission_id`, and `User::hasPermission()` is not yet used anywhere. Fine-grained enforcement can be tightened once a user-permission assignment UI exists, exactly as noted in `docs/payments/payment-permissions.md`.

## Future API ordering

The integration point is a new gateway called after `createProcurementOrder`:

```php
$order = $procurement->createProcurementOrder($quantities, $actor);
$gateway->submit($order);   // not implemented in this stage
```

`MobileSentrixProcurementService` is free of Blade and controller concerns, so the gateway can be added without touching Shop or Repair payment logic, and without schema changes: `supplier_order_number`, `paid_at`, `payment_amount`, tracking and status fields are already in place for an API response to populate.
